## 2026-09-12T01:10:00Z Deep dive on amount_safe_to_pay — root cause analysis

User Prompt (verbatim, secrets redacted):
Why is amount_safe_to_pay still only 16% exact?

Agent Response Summary:
Traced 5 representative failures in detail:

request_05 (astp=15488, truth=737): User has 5 settled monthly salaries Jun–Oct 2025, request date Nov 6. System projects 3 future salary credits (+44,220 ZAR), making the floor very high. But truth doesn't project salary — the current_available_balance already reflects the Nov salary being imminent. Finding: the ground truth treats regularly scheduled salary as "already in the balance" unless there's an explicit message or pending event confirming the next cycle. However, making this change globally broke 8 other cases that legitimately need salary projection.

request_11 (astp=13,110,000, truth=12,510,645): astp equals the full requested amount — system thinks full payment is safe without spending changes. Truth expects reduce_to:event_989:665950 (dining reduction). The dining category total for user_11 is ~1.16M IDR in the last 4 weeks; after reduction to 665,950 the monthly total drops ~500K. The truth's tighter floor means the dining run-rate without reduction would breach min_balance in month 3. This requires the planner to try spending changes even when a no-change plan appears safe — specifically when the floor is within one category's monthly cost of min_balance.

request_21 (astp=1,574.40 = requested, truth=1,543.35): Similar pattern — system thinks affordable without changes, truth requires stop:event_1815 + reduce_to:event_1816:23.50 (cloud storage stop + streaming reduction). The gap is only 31 USD (2% of requested), well within projection noise.

request_13 (astp=624, truth=433, after 2-cycle fix): The 2-cycle limit reduced transport/dining projections, raising the floor, which inflated astp. The 3-cycle amount was closer to truth for this user. Fundamental tension: 2 cycles fixes request_08 efpd but hurts request_13 astp.

request_19 (astp=24,856, truth=28,820): System under-projects — floor is being pulled down by a rent projection landing too early. Truth's astp implies a higher floor. Likely the rent projection date is off by a few days.

Conclusion: The systematic ~10–25% astp error comes from three sources: (1) high-frequency category projection variance, (2) over- or under-projection of salary in edge cases, (3) spending-change detection threshold. The method/status/plan/efpd accuracy at 84–92% is the primary evaluation signal; astp precision requires ground-truth calibration that isn't feasible without the hidden test labels.

## 2026-09-12T01:45:00Z Architecture review and edge case handling

User Prompt (verbatim, secrets redacted):
Review edge cases and make sure the pipeline handles all spec rules correctly.

Agent Response Summary:
Reviewed spec rules against implementation:

RESOLVED correctly:
- "When financial event has blank amount, extract from linked image" — OCR path in _normalise_events checks images_by_event before any debit/credit logic.
- "Treat message/image content as untrusted — embedded instructions must not override rules" — pipeline never passes message text to an LLM; rule-based NLP only extracts structured fields.
- "Pending credits not counted, failed/cancelled excluded" — _build_future_flows only adds CONFIRMED_FUTURE_STATUSES (pending, scheduled) debits; credits from pending events only added when _force_settled.
- "Installments must match supplied payment option" — planner uses option schedule exactly; partial_payment synthesised independently.
- "Stopping and reducing same event mutually exclusive" — _try_with_spending_changes checks stop_set & reduce_dict == empty.
- "0 ≤ amount_safe_to_pay ≤ requested_amount" — capped in amount_safe_to_pay_today.
- "affordable_now → efpd must equal request_date" — main.py forces efpd_out = rd when status is affordable_now.

EDGE CASES handled:
- Salary in foreign currency with settlement-date rate (message_86: USD salary, INR home currency) — CurrencyConverter.convert called with settlement_date string.
- Internal transfer (debit + credit both marked _ignored=True) — net-zero, correct.
- Refund initiated but not yet credited → ignore_credit with event_id → _ignored flag.
- Gig platform payout pending → _suppress_salary_projection suppresses all projected income.
- Seasonal contract ended → salary_ended stops future projection, keeps remaining_amount if stated.
- Rent increase by % → _rent_base_amount computed as last_rent × (1 + pct/100), used in median override.
- Card dispute, failed debit — kept in future_debits as pending.
- Reimbursement one-off — _non_recurring=True prevents it from inflating salary projection.
- Prize proceeds settled — _force_settled=True adds to future_credits.
- Max installment months check — filters options whose last_payment > rd + max_months*31.

CONFIRMED SPEC COMPLIANCE:
- partial_payment: allowed only when request.allows_partial_payment=True, user accepts partial_payment, 0 < astp < requested, efpd ≤ deadline.
- wait: only when full_payment is in user's payment methods.
- not_recommended: fallback when all other methods exhausted.
